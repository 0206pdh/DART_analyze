# ADR-0017: Phase 2 분석은 동기 요청으로 처리한다

- 상태: 채택
- 날짜: 2026-09-04

## 문제와 제약

AI 호출은 수 초 이상 걸리거나 실패할 수 있다. 다만 초기 단일 서버에서 Redis와 워커를 운영하면 고정비와 장애 지점이 늘어난다.

## 판단 기준

최소 서버 비용, 사용자 경험, 실패 복구, 운영 복잡도, 예상 초기 트래픽을 기준으로 본다.

## 비교

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| FastAPI 동기 요청 | 구성과 배포가 단순, 추가 인프라 없음 | 요청 중 연결 유지, 장시간 작업에 약함 | 채택 |
| FastAPI BackgroundTasks | 응답 분리 가능 | 프로세스 재시작 시 유실, 작업 상태 관리 부실 | 제외 |
| Redis + Celery/RQ | 재시도·작업 상태·수평 확장 | 서버와 운영비 증가 | 보류 |
| 관리형 큐/서버리스 작업 | 탄력적 확장 | 공급자 종속과 호출·대기 구성 증가 | 보류 |

## 결정

초기에는 60초 타임아웃과 1회 SDK 재시도를 둔 동기 API로 처리한다. UI는 진행 상태와 재시도 가능한 오류를 보여준다. 분석 레코드는 성공한 결과만 커밋한다.

## 감수하는 단점과 재검토

동시 호출이 늘면 웹 워커가 점유된다. p95가 15초를 넘거나 동시 분석 때문에 일반 API가 지연되거나 월 100건 이상의 실패 재시도가 발생하면 DB 작업 테이블 기반 워커를 먼저 검토하고, 규모가 커질 때 Redis 큐로 옮긴다.
