# ADR-0008: 초기 운영 데이터베이스는 SQLite를 사용한다

- 상태: 채택
- 날짜: 2026-09-04

## 맥락

Phase 1은 약 12만 개의 회사 원장, 공시 메타데이터와 분석 캐시를 저장한다. 회사 원장은 배치가 쓰고 사용자 요청은 주로 읽는다. 초기에는 단일 서버로 배포하며 운영비를 최소화해야 한다.

## 판단 기준

- 월 고정비와 관리 작업
- 현재 읽기 중심 부하 처리
- 백업과 복구 가능성
- SQL 기능과 데이터 무결성
- PostgreSQL로 이전 가능한가
- 단일 서버 배포 적합성

## 비교

| 후보 | 비용·운영 | 장점 | 단점 | 평가 |
|---|---|---|---|---|
| SQLite + 영구 볼륨 | 별도 DB 비용 없음 | 설정이 거의 없고 백업이 단순, 현재 읽기 중심 부하에 충분 | 한 시점에 writer 1개, 다중 서버 공유 부적합 | 채택 |
| 서버 내 PostgreSQL | 서버 비용 내 운영 가능 | 높은 동시성, 검색·확장 기능 | 같은 저사양 서버에서 메모리와 운영 부담 증가, 직접 백업 필요 | 전환 후보 |
| 관리형 PostgreSQL | DB 월 고정비 추가 | 자동 백업·패치·고가용성 옵션 | MVP에서 애플리케이션 서버보다 DB 비용이 커질 수 있음 | 성장 후 후보 |
| 서버리스 DB | 사용량 기반 또는 무료구간 | 관리 부담이 낮고 확장 편리 | 공급자 종속, 휴면·연결 제한·가격 변경 가능성 | 배포 플랫폼 확정 시 재검토 |
| 문서 DB | 별도 서비스 비용 | 비정형 문서 저장이 편함 | 회사 검색·공시 관계·마이그레이션에 관계형 DB보다 이점이 적음 | 제외 |

## 결정

운영 초기에는 서버의 영구 볼륨에 SQLite 파일 하나를 둔다. WAL 모드, foreign key 검증, busy timeout을 모든 연결에 적용한다. 원문 ZIP 자체는 DB에 넣지 않고 파일 캐시 또는 향후 객체 스토리지에 저장하며 DB에는 메타데이터와 경로만 둔다.

개발과 운영 모두 같은 SQLAlchemy 모델을 사용하고 SQLite 전용 SQL 사용을 제한해 PostgreSQL 이전 비용을 낮춘다.

## 감수하는 단점

- 쓰기 작업은 직렬화되며 긴 트랜잭션이 전체 쓰기를 막을 수 있다.
- 애플리케이션을 여러 서버로 수평 확장할 수 없다.
- 서버 디스크 장애에 대비해 별도 백업이 필수다.

## 운영 규칙

- DB 파일은 컨테이너 내부 임시 파일시스템이 아닌 영구 볼륨에 둔다.
- 매일 SQLite online backup을 다른 저장소로 복사하고 복구 테스트를 한다.
- 회사 원장 upsert는 짧은 배치 트랜잭션으로 나눈다.
- 원문 다운로드와 AI 호출 중에는 DB 쓰기 트랜잭션을 열어두지 않는다.

## PostgreSQL 전환 조건

다음 중 하나가 실제로 발생하면 ADR을 새로 작성해 PostgreSQL로 전환한다.

- 애플리케이션 인스턴스가 2개 이상 필요함
- 쓰기 잠금 대기로 요청 오류나 p95 지연 목표 위반이 반복됨
- 동시 분석 저장 작업이 지속적으로 증가함
- DB를 애플리케이션 서버와 독립적으로 확장·복구해야 함
- PostgreSQL 전문검색이나 인덱스 기능이 평가에서 명확히 필요함
